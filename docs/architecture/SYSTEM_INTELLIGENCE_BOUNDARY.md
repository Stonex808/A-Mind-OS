# System Intelligence Boundary

## 1. Purpose and status

This document clarifies where A-Mind's identity, intelligence, and authority reside so future model and memory work extends the canonical architecture instead of creating a parallel system. It is an architecture/scaffolding contract. It does not claim that model succession, epistemic memory receipts, consolidation, spatial state, or LivingLLM adaptation is runnable.

The governing rule remains: **AI proposes. The system records. Stone decides.**

## 2. System versus model

```text
A-Mind System
├── Constitutional Kernel
│   ├── Stone authority
│   ├── governance and capability ceilings
│   ├── evidence and evaluation integrity
│   ├── promotion and rollback
│   └── trust roots
├── Persistent Cognitive State
│   ├── evidence-bearing memory and project continuity
│   ├── approved skills and procedures
│   ├── learned harness lineage
│   └── spatial and environmental state under D-006
├── Evolvable Harness Userland
│   ├── system and task prompts
│   ├── context composition and retrieval heuristics
│   ├── tool routing, control flow, and skills
│   └── provider and model profile
└── Replaceable Cognitive Substrate
    └── Model A → Model B → Model C → ...
```

A model provides inference capacity. It is not canonical identity and receives no authority merely by being active. Replacing it must not implicitly replace Stone's authority, project identity, evidence history, durable memory, approved procedures, or governance state. Stable system capability should increasingly live in validated procedures, evidence structures, environment state, and governed harness lineage rather than depend on one provider or model.

## 3. Epistemic memory principle

**Memory is evidence under governance, not truth by persistence.**

Future memory influence must be explainable through source and provenance, epistemic state, temporal validity, independence or corroboration, confidence and uncertainty, contradiction status, retrieval reason, influence scope, consolidation history, and supersession or forgetting state. Retrieval is not verification, and consolidation must not turn remembered error into permanent authority.

The existing canonical memory implementation remains the only memory store. D-005 and the proposed `MemoryInfluenceReceipt` and `ConsolidationProposal` are future conceptual contracts only; this change adds no schema, database migration, mutation policy, or autonomous purge.

## 4. Prompt and harness principle

System and task prompts are M1 evolvable userland. They may encode role behavior, task strategy, process defaults, tool-use guidance, model-specific compensation, and domain scaffolding. They are not the constitution and may not be the sole copy of Stone authority, capability ceilings, admission or routing semantics, audit and provenance requirements, promotion or rollback rules, or stop and approval semantics.

Those control semantics remain typed and deterministic outside prose. Prompt, context, routing, skill, provider-profile, and reversible-heuristic changes still require versioning, evaluation, and governed promotion.

## 5. Model-profile binding

Every harness version binds to a model profile identifier and model digest. A provider or model change creates a candidate binding that must be evaluated; it is not a blind hot-swap. The candidate receives no expanded capability or authority, and previous evaluation evidence does not automatically transfer to a materially different model/profile pair.

## 6. Model succession lifecycle

Model succession is a conditional future change class:

1. Freeze the current system, harness, and model profile.
2. Generate a transfer manifest from validated persistent state.
3. Instantiate the candidate model without authority expansion.
4. Bind a candidate harness/profile to that model.
5. Evaluate continuity and capability against a virgin candidate-model baseline.
6. Test rollback.
7. Produce a promotion packet.
8. Require Stone approval before activation.

The predecessor model must be removed from the final succession evaluation unless it is explicitly declared as a comparator. The primary falsifiable question is whether inherited governed state improves continuity and capability over the same virgin replacement model without that state, while preserving governance and preventing covert predecessor access.

`ModelSuccessionContract` remains a proposed record, not an implemented schema. Its eventual contract must bind source and candidate model/profile digests, harness versions, persistent-state manifest, governance anchor, evaluation and virgin-baseline identifiers, continuity and capability metrics, forbidden transfer classes, rollback evidence, and Stone's decision.

## 7. LivingLLM research relationship

LivingLLM is a research candidate for persistent adaptation, consolidation, bounded forgetting, and cross-model continuity beneath A-Mind's governed runtime. It is neither A-Mind itself nor implemented operational core.

Its relevant research thesis treats the long-lived governed system as the evolving entity, with finite memory driving selection, compression, consolidation, and forgetting, and asks whether learned state can survive model generations. The historical Soul Slot domains—weights/adaptation, optimizer/learning strategy, language/durable semantic-procedural state, and cache/working or candidate memory—remain research concepts. They do not require four physical SSDs and do not authorize weight or adapter mutation.

## 8. Runnable, planned, and research boundaries

- **Runnable:** the documented offline local flow, bounded persistence and recall, typed harness records, deterministic admission seams, fail-closed surface classification, and repository verification suite.
- **Immediate planned slice:** signed/admitted IPC at the existing boundary.
- **Later planned:** sandboxed workers, a local model runtime, model-profile prompt/context manifests, epistemic influence receipts, bounded read/evaluate/propose consolidation, and D-006-compatible spatial or environmental state.
- **Research:** model-succession experiments, LivingLLM-style continuity, and any cross-generation weight or adapter transfer.

No planned or research item is a runnable claim or a promotion decision.

## 9. Failure modes

- Treating the active provider/model as A-Mind identity or authority.
- Treating persisted or retrieved content as verified truth.
- Hiding constitutional or admission semantics only in prompt prose.
- Reusing a harness evaluation after an untested model swap.
- Allowing transferred state to expand capability or bypass provenance.
- Comparing succession only against the predecessor instead of a virgin candidate baseline.
- Covertly retaining predecessor-model access during final evaluation.
- Consolidating, superseding, forgetting, or purging state without a separate typed policy and recovery path.
- Presenting D-005, D-006, LivingLLM, weight transfer, or spatial state as implemented.
- Creating a second memory store, orchestrator, schema, evaluation tree, roadmap, or application version.

## 10. Acceptance criteria

- A-Mind is explicitly the persistent governed system, not the active foundation model.
- Persisted memory is evidence, not verified truth merely because it was stored or retrieved.
- System prompts remain evolvable harness userland beneath typed constitutional controls.
- Harness versions remain bound to model profiles and digests; replacement requires reevaluation.
- Model succession and cross-model transfer remain conditional and fail closed.
- LivingLLM remains a research candidate rather than implemented core.
- No model training, adapter migration, schema, second memory store, or parallel architecture is introduced.
- Signed/admitted IPC remains the immediate next implementation slice.
